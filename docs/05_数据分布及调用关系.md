# 05 — 数据分布及调用关系

> 本文档梳理 VK Dispatcher 系统中各类数据的存储位置、读写时机、以及调用关系。
> 重点分析 `status_map.json` 状态映射不一致问题的根因。

---

## 1. 问题背景：status_map 不一致

### 1.1 问题现象

`status_map.json` 中记录的状态 ID（UUID）与 VK 云端实际状态 ID 不一致，导致：
- `update_issue_status()` 调用失败（VK 返回 400/404）
- 状态流转无法正确触发
- Dispatcher 状态机卡死

### 1.2 根因分析

**核心问题：status_map 是本地缓存的"快照"，VK 云端状态 ID 可能发生变化**

可能的触发场景：
1. **VK 项目迁移** — 项目从一个 VK 组织迁移到另一个，状态 ID 重新生成
2. **VK 版本升级** — VK 后端升级时重新初始化了状态表
3. **手动修改状态配置** — 用户在 VK UI 中添加/删除/重命名了状态
4. **多设备同步延迟** — status_map.json 被某设备更新，其他设备未同步
5. **项目初始化不完整** — 初始化时未正确发现状态映射

## 2. 数据存储位置总览

| 数据类型 | 存储位置 | 存储格式 | 所有者 | 读写频率 |
|---------|---------|---------|--------|---------|
| Issue/Project/Status | VK 云端（PostgreSQL） | 云数据库 | VK SaaS | 实时 |
| 本地 Workspace/Session | `~/.local/share/vibe-kanban/db.v2.sqlite` | SQLite | VK 本地服务 | 高频 |

| 调度状态持久化 | `<project>/.vk/dispatcher_state.json` | JSON | Dispatcher | 高频（每轮轮询） |
| 多设备共享状态 | `<maw-dir>/.vk/state_<project>.json` | JSON | Dispatcher | 高频（同步） |

## 3. VK 云端数据（权威数据源）

### 3.1 数据结构

VK 云端维护以下核心数据（存储在 VK SaaS 的 PostgreSQL 中）：

```json
// Project
{
  "id": "65f08fde-be22-47d2-bae7-405dcf96685a",
  "name": "hci-troubleshoot-platform",
  "organization_id": "2ac991e1-a835-41ff-bbc1-2605d25f8375"
}

// Status（每个 Project 有独立的状态定义）
[
  {"id": "c7d272b2-5364-4361-a59a-0d3577957d1e", "name": "Backlog", "order": 0},
  {"id": "3e0bb954-b8a1-48c5-befb-d8d44208c727", "name": "To do", "order": 1},
  {"id": "cdf6854a-fb32-4229-8b76-ec7f5cf3319a", "name": "In progress", "order": 2},
  {"id": "2d54a487-e9e8-4ff0-8215-8ceac6529b28", "name": "In review", "order": 3},
  {"id": "4992cfb3-787e-4399-bfec-72c4c257dba4", "name": "Done", "order": 4},
  {"id": "34309404-a601-4771-ac98-eb0de63cc7ec", "name": "Cancelled", "order": 5}
]

// Issue
{
  "id": "abc123...",
  "title": "Fix login bug",
  "status": "In progress",           // 状态名称（仅 REST 返回）
  "status_id": "cdf6854a-...",       // 状态 UUID（REST/MCP 都返回）
  "project_id": "65f08fde-...",
  "description": "..."
}
```

### 3.2 访问方式

| 端点 | 协议 | 返回数据 |
|------|------|---------|
| `GET /api/remote/issues?project_id=<id>` | REST | Issue 列表（含 `status` + `status_id`） |
| `GET /api/remote/issues/{id}` | REST | Issue 详情（含 `status` + `status_id`） |
| `PATCH /api/remote/issues/{id}` | REST | 更新 Issue（只接受 `status_id`，不接受名称） |
| `mcp://update_issue` | MCP | 更新 Issue（接受 `status` 名称，自动转换） |
| `mcp://create_issue` | MCP | 创建 Issue（返回新 Issue ID） |

**关键点**：
- REST API 更新状态时**必须使用 `status_id`（UUID）**，不接受状态名称
- MCP API 更新状态时**可以使用状态名称**，由 VK MCP Server 内部转换

## 4. 本地文件存储

### 4.1 `.vk/dispatcher.json` — 调度器配置

**位置**：`<project-dir>/.vk/dispatcher.json`

**用途**：存储项目级配置（project_id, repo_id, 自动化开关等）

**读写时机**：
- **读**：Dispatcher 启动时（`DispatcherConfig.load()`）
- **写**：用户手动编辑 / `init.sh` 初始化时

**数据结构**：
```json
{
  "organization_id": "2ac991e1-a835-41ff-bbc1-2605d25f8375",
  "project_id": "65f08fde-be22-47d2-bae7-405dcf96685a",
  "repo_id": "24e156dd-c300-4573-a234-c7d0ed619ec8",
  "main_branch": "main",
  "poll_interval": 30,
  "vk_port": 9527,
  "auto_start_coding": true,
  "auto_start_review": true,
  "auto_merge": true,
  "auto_create_pr": true,
  "pr_merge_method": "squash",
  "default_coder_executor": "CLAUDE_CODE",
  "cross_review_map": {
    "CLAUDE_CODE": "CODEX",
    "CODEX": "CLAUDE_CODE"
  },
  "max_coding_retries": 2,
  "max_review_retries": 2,
  "max_coding_wait_minutes": 60,
  "max_review_wait_minutes": 15
}
```

**调用函数**：
- `DispatcherConfig.load(config_path, project_dir)` — 加载配置（`core.py:96-145`）

### 4.2 `.vk/status_map.json` — 状态映射缓存

**位置**：`<project-dir>/.vk/status_map.json`

**用途**：缓存状态名称 → 状态 UUID 的映射（用于 REST API 调用）

**读写时机**：
- **读**：Dispatcher 启动时（`DispatcherConfig.load()` 内部）
- **写**：自动发现完成后（`_auto_discover_status_map()`）

**数据结构**：
```json
{
  "Backlog": "c7d272b2-5364-4361-a59a-0d3577957d1e",
  "To do": "3e0bb954-b8a1-48c5-befb-d8d44208c727",
  "In progress": "cdf6854a-fb32-4229-8b76-ec7f5cf3319a",
  "In review": "2d54a487-e9e8-4ff0-8215-8ceac6529b28",
  "Done": "4992cfb3-787e-4399-bfec-72c4c257dba4",
  "Cancelled": "34309404-a601-4771-ac98-eb0de63cc7ec"
}
```

**调用函数**：
- `DispatcherConfig.load()` — 启动时加载（`core.py:102-109`）
- `_auto_discover_status_map()` — 自动发现并写入（`core.py:1604-1657`）
- `VKRestClient.update_issue_status()` — 使用映射更新状态（`vk.py:112-138`）

**问题根因**：
1. `status_map.json` 是本地缓存，不会自动更新
2. VK 云端状态 ID 变化后，本地缓存失效
3. Dispatcher 启动时若 `status_map.json` 存在，**不会重新发现**

## 5. 本地数据库存储（SQLite）

### 5.1 `db.v2.sqlite` — VK 本地数据

**位置**：`~/.local/share/vibe-kanban/db.v2.sqlite`

**用途**：VK 本地服务维护的 Workspace、Session、执行进程状态

**所有者**：VK 本地服务（Dispatcher 只读访问）

**关键表结构**：

```sql
-- Workspace（工作空间）
CREATE TABLE workspaces (
  id TEXT PRIMARY KEY,
  name TEXT,
  branch TEXT,
  container_ref TEXT,  -- worktree 路径
  archived BOOLEAN
);

-- Session（会话）
CREATE TABLE sessions (
  id TEXT PRIMARY KEY,
  workspace_id TEXT,
  created_at TEXT
);

-- Execution Process（执行进程）
CREATE TABLE execution_processes (
  id TEXT PRIMARY KEY,
  session_id TEXT,
  run_reason TEXT,     -- 'codingagent' / 'cleanupscript' / 'setupscript'
  status TEXT,         -- 'running' / 'completed' / 'failed' / 'killed'
  exit_code INTEGER,   -- NULL 表示运行中或 VK 重启 artifact
  dropped BOOLEAN,     -- TRUE 表示已清理
  started_at TEXT
);

-- Repo（仓库配置）
CREATE TABLE repos (
  id TEXT PRIMARY KEY,
  name TEXT,
  setup_script TEXT,
  cleanup_script TEXT
);

-- Workspace-Repo 关联
CREATE TABLE workspace_repos (
  workspace_id TEXT,
  repo_id TEXT
);
```

**调用函数**（`vk_db.py`）：

| 函数 | 用途 | 调用位置 |
|------|------|---------|
| `get_latest_process(branch, run_reason)` | 获取最新执行进程 | `_check_stuck_coding()`, `is_qg_passed()` |
| `has_cleanup_script(branch)` | 检查是否配置 QG 脚本 | `is_qg_passed()` |
| `is_qg_passed(branch)` | 判断 QG 是否通过 | `_check_pending()` |
| `is_agent_running(branch)` | 检查 Agent 是否运行中 | `_check_stuck_coding()` |
| `get_repo_scripts_by_id(repo_id)` | 获取仓库脚本配置 | `_ensure_repo_scripts()` |
| `get_worktree_path(branch)` | 获取 worktree 路径 | 多处 |
| `is_coding_timed_out(branch, max_minutes)` | 检测超时 | `_check_stuck_coding()` |

## 7. status_map 不一致的完整数据流分析

### 7.1 正常流程

```
1. Dispatcher 启动
   │
   ├─► DispatcherConfig.load()
   │     │
   │     ├─► 读取 .vk/dispatcher.json
   │     │
   │     └─► 读取 .vk/status_map.json
   │           │
   │           └─► config.status_map = {"To do": "uuid-123", ...}
   │
   ├─► 构建反向映射
   │     _status_id_to_name = {v: k for k, v in config.status_map.items()}
   │
   └─► 进入主循环
         │
         └─► poll_once()
               │
               ├─► REST list_issues() 获取 Issue 列表
               │     │
               │     └─► 返回: [{status_id: "uuid-123", status: "To do"}, ...]
               │
               └─► 用 _status_id_to_name 转换 status_id → 状态名称
```

### 7.2 问题流程（status_map 过期）

```
1. VK 云端状态 ID 变化（例如项目迁移）
   │
   └─► 新状态 ID: {"To do": "uuid-NEW", ...}

2. Dispatcher 启动
   │
   └─► 加载旧的 status_map.json
         config.status_map = {"To do": "uuid-OLD", ...}

3. poll_once() 中调用 update_issue_status()
   │
   ├─► 使用旧 status_map 转换
   │     status_id = status_map["To do"]  # 返回 "uuid-OLD"
   │
   └─► REST PATCH /api/remote/issues/{id}
         {"status_id": "uuid-OLD"}  # VK 云端返回 400/404
```

### 7.3 修复机制（自动发现）

```
1. _auto_discover_status_map() 触发条件
   │
   ├─► status_map.json 不存在
   │
   └─► 手动调用（未来可增加：启动时校验 + 定期刷新）

2. 发现流程
   │
   ├─► 快速路径：get_status_map_from_issues()
   │     │
   │     └─► 从现有 Issue 中读取 status + status_id
   │
   └─► 探针路径：mcp.discover_status_map()
         │
         ├─► 创建临时 Issue
         ├─► 循环更新各状态
         ├─► 从 REST 读取 status_id
         └─► 删除临时 Issue

3. 写入并热更新
   │
   ├─► 写入 .vk/status_map.json
   │
   └─► 热更新 config.status_map + _status_id_to_name
```

## 9. 建议改进

### 9.1 防止 status_map 不一致

1. **启动时校验**：在 `Dispatcher.__init__()` 中调用快速路径验证 status_map
   ```python
   def _validate_status_map(self):
       """启动时校验 status_map 是否与云端一致"""
       cloud_map = self.rest.get_status_map_from_issues(self.config.project_id)
       for name, local_id in self.config.status_map.items():
           if name in cloud_map and cloud_map[name] != local_id:
               logger.warning("status_map 不一致: %s 本地=%s 云端=%s",
                   name, local_id[:8], cloud_map[name][:8])
               # 触发重新发现
               self._auto_discover_status_map()
               return
   ```

2. **定期刷新**：每 N 轮轮询后刷新 status_map（可选）

3. **错误时自动恢复**：`update_issue_status()` 失败时自动触发重新发现

### 9.2 增强可观测性

1. **记录 status_map 来源**：在 `status_map.json` 中增加 `discovered_at` 字段
2. **增加指标**：记录 status_map 命中/未命中次数
