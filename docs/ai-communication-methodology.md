# AI 协作沟通方法论

> 记录日期：2026-03-09  
> 本文总结在与 AI 编程助手协作设计复杂系统时，经验证有效的沟通方式。

---

## 1. 核心原则：问题诊断优先于解决方案

**错误模式**：直接描述想要的解决方案 → AI 实现 → 反复修 bug  
**正确模式**：描述现象和痛点 → 共同诊断根因 → 确认根因后再实现

### 实操方式

用"现象 + 发生频率 + 已尝试的方法"三要素描述问题：

```
现象：Reviewer 的 APPROVED/CHANGES_REQUESTED 判断经常出错
频率：大约 30% 的情况会误判
已尝试：调整 prompt 关键词、加强格式要求——都没有根本解决
```

让 AI 提出根因假设，你来确认或否定，直到双方对根因达成共识后再动手。

---

## 2. 挑战 AI 的结论（苏格拉底法）

AI 的第一个回答通常是"症状级"的，需要反复追问才能到达"根因级"。

### 有效的追问模式

| 追问角度 | 示例 |
|---------|------|
| 质疑根因 | "你说 prompt 不够清晰，但即使 prompt 更清晰，Agent 能100%遵守吗？" |
| 追问为什么 | "为什么会这样？背后的机制是什么？" |
| 反例施压 | "我们已经试过这个方案了，结果是 X，你怎么解释？" |
| 逼迫分类 | "哪些情况下你的方案会失败？失败率大概是多少？" |

### 案例：从症状到根因

```
初始答案：Reviewer prompt 格式不够严格 → 加强 prompt
追问1：即使 prompt 更严格，Agent 概率上能100%执行吗？
答案：不能，LLM 本质上是概率模型
追问2：那多 Agent 链条上，每个节点误差叠加会怎样？
答案：误差指数级叠加，链条越长越不可靠
根因：系统依赖"概率性"信号（Agent NL 输出）做确定性判断 → 必然有 bug
```

## 3. 信号可信度分级

在设计 Agent 间通信协议时，首先建立信号可信度框架：

```
级别 1（基础设施级）：由平台/系统自动写入，不经过 Agent
  例：exit_code、HTTP 状态码、数据库字段、PR merge status

级别 2（工具调用级）：Agent 主动调用 API/工具写入结构化数据
  例：Agent 调用 MCP update_issue 修改 status
  → 可信，但有"Agent 不调用"的失败模式，需超时检测兜底

级别 3（文件/约定级）：Agent 写入约定格式的文件或特定路径
  → 不可信，格式遵守率低，工具调用失败率高

级别 4（自然语言级）：Agent 在回复中用关键词表达意图
  → 最不可信，歧义高、格式随机、截断丢失
```

**设计原则**：系统状态流转只依赖级别 1 和级别 2 的信号。级别 3/4 只用于人类可读的日志。

## 4. 方案评估框架

提出候选方案后，用以下维度对比：

| 维度 | 问题 |
|-----|------|
| 信号可信度 | 关键信号属于哪个级别？ |
| 失败模式 | 什么情况下会失败？失败是否可观测？ |
| 可恢复性 | 失败后能自动恢复还是需要人工介入？ |
| 复杂度 | 实现和维护成本如何？ |
| 依赖 | 依赖外部系统哪些行为假设？这些假设可能被打破吗？ |

## 5. 悲观等待 vs 乐观推进

在 Agent 编排系统中，两种范式的选择会决定系统的长期稳定性：

### 乐观推进（Optimistic Forward）
```
信号不明确 → 猜测最可能的结果 → 继续推进
```
- 优点：在理想情况下快速
- 缺点：错误悄悄积累，最终以不可预期的形式暴发，难以调试

### 悲观等待（Pessimistic Wait）
```
信号不明确 → 停止 → 等待明确信号 → 超时 → 告警 → 人工介入
```
- 优点：失败模式可观测、可预期、可调试
- 缺点：需要额外的超时和重试机制

**推荐**：对于涉及外部状态变更的操作（写 DB、创建 PR、发邮件），始终用悲观等待。

## 6. 与 AI 协作的最佳实践

### 进入深度分析模式

让 AI 分析大量上下文时，明确要求：

```
"请深入分析源码，不确定的地方直接读文件，不要猜测。"
"找到证据再说结论，不要基于假设给建议。"
```

### 分阶段确认

不要一次性让 AI 实现所有内容。先确认设计，再实现：

```
第一步：描述系统，让 AI 找出所有问题
第二步：对每个问题讨论根因，确认
第三步：讨论解决方案，确认方向
第四步：开始分模块实现，每模块实现后确认
```

### 让 AI 主动发现依赖

实现前让 AI 读相关源码：
```
"在实现 reviewer.md 之前，先读 VK 的 MCP 源码，确认 update_issue 工具的参数格式和可用性。"
```
这比让 AI 基于文档或假设来实现要可靠得多。

### 验证计划先于实现

每个功能点实现前，先讨论"我们怎么验证它工作了"。若无法设计清晰的验证步骤，说明设计本身还不够清晰。
